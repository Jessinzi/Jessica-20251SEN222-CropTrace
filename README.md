## 1. Problem Statement
Agricultural products often face challenges such as poor tracking, stock
mismanagement, delays, and losses as they move from farms to processing
industries, warehouses, and sellers. There is no centralized record of crop
transportation, processing, storage, and distribution, which makes it
difficult to trace where losses occur, hold anyone accountable, or protect
product quality. This project proposes a centralized Oracle database system
to monitor crop transportation, processing, storage, and distribution,
providing accurate records of product quantities and movements throughout
the supply chain.
---
## 2. Objectives
**Main objective:**  
To design and build a working Oracle database with PL/SQL that tracks
agricultural products end-to-end — from farm through transport, storage, and
distribution — and enforces supply-chain business rules.
**Specific objectives:**
1. To normalize real agricultural supply-chain data into 3NF tables with a
   documented ERD and data dictionary.
2. To implement PL/SQL procedures, functions, cursors, packages, and
   triggers that record movements and automatically flag delays and
   spoilage.
3. To build a user interface connected live to the Oracle database that
   lets users record shipments and quality checks and view alerts raised
   automatically by triggers.

## 4. Innovation — User Interface
**Option chosen:** User interface  
**Tool:** Oracle APEX (bundled with Oracle Database), with Python Streamlit
as a fallback.
**What it does:** A simple web application connected live to the Oracle
database. Business rules stay inside PL/SQL — the interface only calls
procedures and displays results.
1. **Data entry forms.** A clerk records shipments and quality checks. Each
   form calls a PL/SQL procedure (`record_shipment`, `record_quality_check`),
   so every rule is enforced by the database, not the app.
2. **Automatic alerts panel.** When a quality check is recorded with
   spoilage above the threshold, a quality grade below the accepted level,
   or a storage location above 90% capacity, a trigger writes a row to the
   `ALERTS` table. The interface shows these alerts live on a dashboard, so
   staff see problems the moment they are recorded.
3. **Delivery schedule view.** A "Build Schedule" button calls the
   `pkg_automation.build_delivery_schedule` procedure, which ranks batches
   by risk score (spoilage percentage plus transport delay), assigns them to
   drivers up to each driver's per-cycle cap, and shows the resulting
   `DELIVERY_SCHEDULE` in the interface.

## 5. Planned Database Tables
| Table | Purpose | Key columns |
|---|---|---|
| `FARM` | Origin of each product batch | `farm_id` (PK), `region`, `farm_name` |
| `CROP` | Crop master data | `crop_id` (PK), `crop_name`, `category` |
| `PRODUCTION_BATCH` | Quantity produced per batch | `batch_id` (PK), `farm_id` (FK), `crop_id` (FK), `yield_quantity_kg`, `supply_chain_stage` |
| `SHIPMENT` | Movement between stages | `shipment_id` (PK), `batch_id` (FK), `transport_delay_hours` |
| `STORAGE` | Storage records and capacity | `storage_id` (PK), `batch_id` (FK), `store_location`, `capacity_kg`, `current_stock_kg` |
| `QUALITY_CHECK` | Quality and loss per batch | `check_id` (PK), `batch_id` (FK), `spoilage_loss_pct`, `quality_grade` |
| `DISTRIBUTION` | Final distribution to sellers | `distribution_id` (PK), `batch_id` (FK), `seller_name` |
| `DRIVER` | Drivers available for delivery | `driver_id` (PK), `driver_name`, `max_deliveries_per_cycle` |
| `DELIVERY_SCHEDULE` | Delivery plan generated by the package | `schedule_id` (PK), `batch_id` (FK), `driver_id` (FK), `priority_rank` |
| `ALERTS` | Alerts raised automatically by triggers | `alert_id` (PK), `batch_id` (FK), `alert_type`, `message`, `is_resolved` |
| `AUDIT_LOG` | Tracks all changes | `log_id` (PK), `table_name`, `action`, `changed_by` |

## 6. Planned PL/SQL Features
| Feature                | Where it is used                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Procedures**         | `record_shipment`, `record_quality_check`, `build_delivery_schedule` — called by the interface when a user submits a form or clicks Build Schedule                                                                                                                                                                                                                                                                                               |
| **Functions**          | `get_batch_risk_score(batch_id)` — combines spoilage percentage and transport delay into one priority score; `get_storage_utilisation(location)` — returns % of capacity used                                                                                                                                                                                                                                                                    |
| **Cursors**            | Loop through batches ordered by risk score to assign drivers in `build_delivery_schedule`                                                                                                                                                                                                                                                                                                                                                        |
| **Packages**           | `pkg_supply_chain` (shipment/storage/quality procedures) and `pkg_automation` (risk scoring, scheduling, alert helpers)                                                                                                                                                                                                                                                                                                                          |
| **Triggers**           | `trg_spoilage_alert` — inserts into `ALERTS` when a quality check exceeds the spoilage threshold or falls below the accepted grade; `trg_storage_capacity_alert` — inserts into `ALERTS` when a storage location exceeds 90% capacity; `trg_driver_load_check` — rejects a schedule entry that exceeds the driver's per-cycle cap; `trg_audit` — writes to `AUDIT_LOG`; `trg_reject_invalid_quantity` — blocks zero/negative shipment quantities |
| **Exception handling** | Custom exceptions for invalid quantity, missing batch, storage over capacity, driver over limit                                                                                                                                                                                                                                                                                                                                                  |
| **Restriction rule**   | A trigger prevents recording a shipment with zero or negative quantity                                                                                                                                                                                                                                                                                                                                                                           |
